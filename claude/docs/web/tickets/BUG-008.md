# BUG-008 — Khóa tài khoản không ép logout phiên đang mở

| | |
|---|---|

| **Service** | auth-service (ảnh hưởng toàn hệ thống — mọi service tin vào JWT do đây phát hành) |
| **Mức độ** | 🔴 Nghiêm trọng |
| **Trạng thái** | ✅ Đã fix tạm (temp fix) — còn phần việc chưa làm, xem "Việc còn lại" |
| **Liên quan** | [04_BUG_TRACKER.md](../04_BUG_TRACKER.md) |

## Mô tả

Admin khóa tài khoản qua `PATCH /api/v1/accounts/:id` với `status=locked` ([accounts.ts:37-72](../../../src/backend/auth-service/src/routes/accounts.ts#L37-L72)), nhưng access token đã phát hành trước đó cho tài khoản này vẫn dùng được bình thường — không có cơ chế nào ép logout ngay lập tức. Tài khoản bị khóa vẫn gọi API được tới khi access token tự hết hạn.

Nguyên nhân gốc: JWT access token là stateless — mọi service (`trip-service`, `call-center`...) chỉ verify chữ ký/hạn token, không có service nào query lại status mới nhất của user theo từng request. `POST /auth/login` có check `status === 'locked'` tại thời điểm đăng nhập, nhưng `POST /auth/refresh` (nơi user lấy access token mới khi cái cũ hết hạn) lại **không** check — đây là lỗ hổng cụ thể đã sửa tạm trong ticket này.

## Fix tạm đã áp dụng

`POST /auth/refresh` ([auth.ts:128-152](../../../src/backend/auth-service/src/routes/auth.ts#L128-L152)) giờ check `user.status === 'locked'` trước khi cấp access token mới, giống hệt cách `/login` đã làm — nếu tài khoản bị khóa, refresh trả về `403` thay vì cấp token mới.

**Giới hạn của fix tạm này**: không phải "logout ngay lập tức". Access token đang cầm trong tay tại thời điểm admin khóa vẫn dùng được bình thường tới khi tự hết hạn (`JWT_ACCESS_EXPIRES_IN`, mặc định **15 phút** — [auth-service/src/config.ts](../../../src/backend/auth-service/src/config.ts)). Chỉ khi client gọi `/auth/refresh` để xin token mới (do token cũ hết hạn) thì lock mới thực sự chặn được. Tức là: độ trễ tối đa giữa lúc admin bấm khóa và lúc user thực sự bị đá ra = thời gian còn lại của access token hiện có, tối đa 15 phút.

## Việc còn lại — cần Redis để đạt "logout ngay lập tức"

Đã khảo sát và quyết định hướng (xem thảo luận, không lặp lại chi tiết ở đây):

- Muốn khóa có hiệu lực **tức thì** (không chờ access token hết hạn), cần thêm 1 middleware check status theo từng request ở **mọi service** xác thực bằng JWT (`trip-service`, `call-center`, `call-logger`, `voice-agent`...), không chỉ riêng `auth-service`.
- Không nên middleware này gọi HTTP đồng bộ sang `auth-service` mỗi request (tạo phụ thuộc cứng, auth-service chậm/rớt là kéo sập toàn hệ thống). Thay vào đó dùng **Redis dùng chung giữa các service** làm nơi lưu cờ `locked:<userId>`:
  - `auth-service` ghi cờ vào Redis ngay khi `PATCH /accounts/:id` set `status=locked` (và xóa cờ khi unlock).
  - Middleware ở mỗi service đọc Redis (rẻ, dưới 1ms) thay vì query DB hoặc gọi auth-service qua HTTP.
- Redis hiện **chưa được triển khai ở đâu trong dự án** (đã kiểm tra: `REDIS_URL` trống ở mọi env, không container/service nào đang chạy) — code cache (`trip-service/src/cache/redis.ts`) mới chỉ là khung, đang chạy fallback in-memory. Cần dựng Redis thật trước khi làm phần này.
- Đề xuất provider: Upstash (free tier 10k lệnh/ngày, 256MB, REST API không cần giữ connection — hợp với `call-center` chạy trên Lambda) hoặc Redis Cloud (free tier 30MB, 30 connections, cũng public endpoint không cần VPC) — cả hai đều tránh được vấn đề AWS ElastiCache chỉ chạy trong VPC (phải thêm NAT Gateway cho Lambda gọi vào, tốn thêm chi phí/độ phức tạp không cần thiết cho quy mô đồ án).
- Cũng cần thêm `redisUrl` vào `auth-service/src/config.ts` (hiện chưa có key này).

## Acceptance Criteria (cho phần việc còn lại)

- [ ] Dựng Redis (Upstash hoặc Redis Cloud), share 1 `REDIS_URL` cho tất cả service liên quan.
- [ ] `auth-service` ghi/xóa cờ `locked:<userId>` trong Redis khi admin khóa/mở khóa tài khoản.
- [ ] Middleware `authenticate` ở từng service (ít nhất `trip-service`; rà thêm `call-center`, `call-logger`, `voice-agent` nếu tự verify JWT riêng) check cờ này sau khi verify JWT, trả 401 nếu bị khóa.
- [ ] Quyết định rõ hành vi khi Redis không kết nối được (fail-open kèm log cảnh báo, hay fail-closed) — không để mặc định ngầm định như fallback in-memory hiện tại của `cache/redis.ts`.
- [ ] Test: khóa tài khoản giữa lúc đang có access token còn hạn → request tiếp theo bị chặn ngay, không phải chờ token hết hạn.

## Ghi chú

Fix tạm trong ticket này đã đóng đúng lỗ hổng cụ thể nêu trong mô tả gốc của BUG-008 (`/auth/refresh` không check status) và đủ dùng cho quy mô đồ án hiện tại nếu chấp nhận độ trễ tối đa 15 phút. Phần "Redis" ở trên là nâng cấp tiếp theo, chưa làm, cần quay lại khi có nhu cầu logout tức thì thực sự.
